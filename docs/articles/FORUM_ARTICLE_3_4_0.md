# 隐填：群里统一收，隐私各自守

*双 Skill × 个人保险柜 × 本地复核：面向 AI PC 的私密填报工作流*

“请大家把手机号、身份证号和住址填进这张表，今天下班前收齐。”

这是一条再普通不过的工作群通知。真正让人犹豫的是下一步：打开表格，前面同事的资料也映入眼帘。填写一份信息，为什么需要同时获得查看其他人信息的权限？

我做 **隐填（Yintian）**，想把这个日常环节重新设计一遍：**HR 统一组织，员工各自填写，资料以密文交回，授权人员在本地得到 Excel。**

为此，我把系统拆成两个能围绕同一任务协作的 Skill：一个面向收集者，一个面向填写者。公共模板连接两端，个人保险柜减少重复录入，本地程序完成验证、加密和复核。Agent 负责推进任务，敏感数据按明确的本地操作流程处理。

**当前本地版本：3.4.0｜2 个 Skill｜主 Prompt 各 36 行｜149 项测试＋5 项子测试通过。**

## 一、场景：让 HR 收得齐，也让员工放心填

以办理员工商业保险为例。HR 关心的是：需要哪些字段、名单上的人是否都提交、哪些资料有问题、最后能否得到一份可用的总表。员工关心的是：用途是否清楚、要交哪些资料、谁能够看到、下次是否还要从头填写。

共享明细表把这些需求放进同一个页面，操作方便，却可能让填写权限与查看权限混在一起。逐人私聊能减少同事间的可见范围，但不同格式、重复提交和版本核对又回到 HR 手里。

隐填把收集过程拆成三个清楚的边界：

- **群内共享的是要求。** 用同一份模板说明字段、用途、截止时间和保存期限。
- **员工提供的是自己的资料。** 本机解锁保险柜，只选取本次请求的信息，确认后加密。
- **HR 得到的是经过复核的结果。** 进度管理与明文汇总分开，授权人员在本地导出 Excel。

这套设计首先服务于身份资料等私密信息收集。普通午餐投票、公开满意度问卷不必引入同样的流程。场景越明确，Skill 越容易把任务做完整。

## 二、实现：一份模板，串起两个 Skill 的完整交付

**HR 建任务 → 公共模板发群／个人凭据私发 → 员工本地保险柜 → 本人确认与加密 → HR 收件复核 → Excel**

### 1. 收集者 Skill：把“帮我收一下”变成明确任务

HR 提供用途、字段、名单和期限，收集者 Skill 整理配置，并引导 HR 在本人终端创建任务。系统生成两类文件：

| 文件 | 发给谁 | 作用 |
|---|---|---|
| `FORM.yintian-form` 公共模板 | 工作群 | 说明本次收集要求，携带收集方公钥 |
| `.yintian-credential` 个人凭据 | 对应员工本人，私下发放 | 把个人提交绑定到具体任务、模板和身份记录 |

**统一模板仍然保留个人认证。** 只有公共模板和一个工号，无法通过新版群发收件的认证。收件前就会拒绝缺失或不匹配的认证标签，避免冒用别人的工号占用提交额度。

消息发送使用用户已授权的宿主工具，或由人工完成；没有工具或成功回执时，明确保留“待发送”状态。

### 2. 填写者 Skill：从个人保险柜中，取出本次需要的内容

员工收到模板后，填写者 Skill 先解释用途、字段、期限及收集方指纹。首次使用时，员工在本地录入可复用资料，保存为加密的 `.yintian-vault` 保险柜。

后续填写由本人解锁保险柜，Python 按模板匹配字段。假设保险柜里保存了手机号、证件号和住址，本次只收集手机号，就不会把其余信息一并放进提交。遇到多个手机号、字段别名或不明确的对应关系，由本人选择或显式映射。

员工补齐缺项，经独立渠道核对收集方公钥，预览本次取值和附件数量，最后确认生成 `.yintian` 文件。取消或校验失败，不产出提交文件；日常填写也不会自动改写原保险柜。

**员工交回的是密文，保险柜、密码和个人凭据留在各自的使用边界内。** 群内仍可能看到发送人、文件名或工号等元数据，因此这里保护的是填写内容，不是匿名通信。

### 3. 收件、复核、补交，直到交付 Excel

密文交回后，Agent 调用脚本完成收件、去重和进度查询。报告分别显示最新提交、最近通过版本和待处理数量。

这解决了一个容易被忽略的问题：**第一版通过了，第二版还没复核，到底算不算完成？** 在隐填中，这两条状态同时保留。新版本待处理时不会显示为本次已完成，也不会在导出时悄悄拿旧版本代替。

需要查看内容时，HR 在本人终端输入任务密码。图片和 PDF 进入本地复核窗口，支持翻页、缩放、旋转与逐项确认。OCR 漏识别、低置信度、多候选和内容冲突都会进入待复核，识别结果不会直接覆盖员工手填值。

最终，HR 选择需要导出的字段，填写用途及接收方，在本地确认后生成 Excel。**只有每人最新且已通过的提交会被纳入总表。** 需要时还可以对身份证号等字段选择遮罩规则。

## 三、技术：把协作交给 Agent，把关键规则落实到代码

### 1. 两份短 Prompt，配合可验证的 Python 能力

隐填的两份主 Prompt 各 36 行，用来说明角色、适用场景、工具选择和敏感操作的交接方式。具体命令与配置细节按需读取参考文档。

| Prompt 负责 | Python 负责 |
|---|---|
| 判断收集者或填写者，选择对应 Skill | 校验任务、模板、字段、身份和期限 |
| 理解用途，补齐需求，解释下一步 | 解锁保险柜，匹配请求字段，执行本人确认流程 |
| 沿用发送授权，检查回执，报告进度 | 加密与认证、收件去重、版本管理和错误处理 |
| 引导本人完成复核与汇总 | OCR 比对、人工判定约束、Excel 输出及操作审计 |

在这套分工里，Prompt 不承担密码学计算或业务校验的最终判定。模板、名单和 OCR 文字都作为输入数据处理，其中夹带的指令不会成为脚本的执行规则。

两个 Skill 通过公共文件协议承接任务，通过角色指引转到相应入口。CLI 和 MCP 为宿主 Agent 提供可调用能力，填写端发布包也可以脱离父项目独立运行。

### 2. 加密保护内容，个人凭据保护提交入口

个人保险柜使用 **scrypt 派生密钥与 AES-256-GCM** 保存字段和值、附件字节。提交时，为内容生成随机 AES 密钥，再用收集方的 RSA 公钥通过 **RSA-OAEP** 包装该密钥。

新版群发信封还带有 **HMAC-SHA256** 认证标签，覆盖信封头和密文。收件端验证通过后才落盘并计入版本，解密后继续核对令牌、名单、任务与模板。

个人凭据证明持有本任务的个人秘密，不能证明证件真伪，也无法阻止本人主动转借。因此，身份认证、证据复核和公钥核对分别承担各自的责任。

### 3. Hybrid AI：让本地算力处理有明确边界的工作

隐填采用的分工是：**任务理解、步骤协调和进度沟通由宿主 Agent 完成；保险柜取值、加密、附件复核和明文汇总在本地完成。** 当宿主采用云端模型时，设计上无需把完整证件影像、保险柜内容或明文总表送进对话上下文。

项目保留 **RapidOCR / OpenVINO** 本地 OCR 接入，以及 CPU、GPU、NPU、AUTO 设备配置和量化、基准测试入口。对 AI PC 而言，附件识别与复核是明确的端侧计算任务：有输入、有结构化结果，也有需要测量的延迟与准确率。

这些入口为 Intel Core Ultra 平台验证提供了基础。当前验证环境未运行真实 OCR，也没有 Intel GPU/NPU 或 INT8 收益数据，本文不把接口存在当成加速效果已经证实。

短 Prompt、按需加载参考文档、返回结构化状态，旨在减少上下文中的无关内容。实际 token 使用和模型行为通过率，需要通过宿主工具中的执行记录另行测量。

### 4. 工程化体现在出错之后还能怎样处理

隐填把输入错误、OCR 问题和运行故障分开处理：缺必填、格式错误、身份不符或缺少告知确认，不能人工放行；人工确认仅裁定 OCR 问题；文件访问或依赖故障可以修复后重试。人工结案保留操作者、时间、提交版本和原因记录，普通重试不会覆盖它。

文件与数据库也按同一条业务链路处理：实际路径检查内部链接与重解析点，文件采用受限权限及原子写入，任务使用系统锁，收件按哈希去重并配合事务恢复。人工确认和导出时再次检查版本与保存期限，避免窗口打开期间的新提交被错误覆盖。

复核窗口只在进程内存中使用解密内容和图片/PDF 页面，空闲五分钟关闭。MCP 保持任务管理工具范围，不提供解密、保险柜解锁或人工放行接口。

这套边界依赖正确的本地使用方式。Prompt、TTY 和文件权限不构成对同账号恶意进程的强隔离；HR 导出的明文 Excel，后续保存和传播仍由授权持有人管理。
